# 0004 — The first scikit-ops segmenter

**Status:** built, and one decision since reversed — the generated parameter
panel is gone. See *The generated panel, and why it was removed* at the end.

The first concrete step of [0001](0001-what-moves-to-scikit-ops.md). One op —
StarDist 2D — appears in the existing global segmenter list, with its parameter
panel generated by magicgui rather than by our own form builder. Everything
else stays exactly as it is.

## Why this one first, and why now

Not because StarDist is the most valuable op to move. Because of napari
versions.

napari-ai-lab is stuck on napari 0.6.6 in every environment that matters,
because micro-sam pulls napari in explicitly and StarDist's TensorFlow stack
constrains what else can be present. Meanwhile napari 0.8 is roughly 4-5x
faster at the sequence-viewer switching this project does constantly (measured;
see `benchmarks/bench_sequence_switch.py`).

So the model stacks are holding the whole application back a napari major
version. Running them in **their own environments** is what unsticks it, and
scikit-ops already does that. This spec is the smallest possible proof that the
arrangement works inside our UI.

## Scope

**In:** one op, `skop.ops.segment.stardist2d_fluo`, registered explicitly,
selectable from the existing combo, parameters rendered by magicgui,
segmenting through the existing `ImageDataModel.segment()` path.

**Out:** training, custom models, progress and cancellation, interactive
segmenters, discovery of ops, and removing anything that exists today.

Explicitly **not** a replacement for `nd_operation_widget.py`. Two form
builders will coexist. The hope is that the generated one eventually wins, but
that is a decision to make after seeing it work, not before.

## Where it plugs in

Three properties of the existing code make this cheap, and they are the reason
this is the right first step:

| | |
| --- | --- |
| The combo is populated from a registry, not a list | `GlobalSegmenterBase.get_registered_frameworks()` — `nd_easy_segment.py:231`. Anything registered appears; no change needed |
| Execution goes through one call | `ImageDataModel.segment(segmenter, sub)` — `nd_easy_segment.py:816`, which calls `segmenter.segment(image, **kwargs)` |
| The parameter panel is one widget in one place | `_create_segmenter_parameter_form()` — `base_nd_app.py:336`, swapped by `set_nd_operation()` on selection |

The only genuinely new capability is **letting a segmenter supply its own
parameter widget**.

## The pieces

### 1. Environment

`pixi/microsam_cellposesam_czi/pixi.toml` gains `scikit-ops` and `skop-napari`
(path dependencies to the siblings, for now).

**appose must come from git main.** `PixiInstallMonitor` landed in
appose-python `3e97f55` and is in no release; 0.11 and 0.12 have no monitor and
report only a final summary. Both scikit-ops and skop-napari already pin main
for this reason. With `appose = "*"` from PyPI the first build is silent, which
is the single worst first-run experience available. Accepted as temporary.

### 2. `Segmenters/GlobalSegmenters/SkopSegmenter.py` — new file

An adapter holding one skop op, satisfying the `GlobalSegmenterBase` contract:

- `segment(image, **kwargs)` — calls skop's runner, returns the label image
- `are_dependencies_available()`, `get_execution_string()` — trivial
- `get_parameter_widget()` — **new optional method**, returns a magicgui
  container built with `skop_napari.build_inputs(spec, annotation_for=..., skip=...)`

`skip` leaves out the image parameter. napari-ai-lab already owns image
selection and passes the array in, so the panel shows only `prob_thresh`,
`nms_thresh`, `normalize`. This also avoids needing napari layer types in a
panel that is not driving layer selection.

### 3. `base_nd_app.py` — one hook

Put `segmenter_parameter_form` in a `QStackedWidget`. On selection change, if
the segmenter provides `get_parameter_widget()`, show that page; otherwise show
the existing `NDOperationWidget`. One `if`, and the two form builders never
touch each other.

### 4. Registration — explicit, not discovered

One line beside the existing `.register()` calls in `launch_nd_ai_lab.py`:

```python
SkopSegmenter.register_op(stardist2d_fluo, name="StarDist2D (scikit-ops)")
```

No `skop.discovery`. Discovery is slow and would flood a list that is
deliberately curated.

## First-run environment builds

The op runs in skop's own environment (`env="stardist-tf"`), which is the whole
point — TensorFlow never enters the napari process. But that environment is
**built on first use**, taking minutes and gigabytes, inside what looks to the
user like a button press.

Handled well this is the feature: no conda wrangling, no shared-memory
plumbing, it simply works. Handled badly it is indistinguishable from a hang,
and the first the user hears of it is a full disk.

**Ask before building.** A dialog on first use, before any work starts:

- which environment is being built and which op needs it
- the directory it will be written to
- roughly how large and how long
- cancel

The directory matters beyond politeness: a user who knows where it lives can
delete it, inspect it, or reuse it. Environments are a resource we are creating
on their machine, and telling them where is the difference between a tool and a
squatter.

**Then show progress.** scikit-ops
[design 0004](../../../scikit-ops/docs/design/0004-build-feedback.md) provides
three subscriptions on `Runner`:

```python
runner.subscribe_build_progress(lambda title, current, maximum: ...)
runner.subscribe_build_output(lambda text: ...)
runner.subscribe_build_error(lambda text: ...)
```

Titles name real phases with real denominators — `Solving`, `Installing conda
packages`, `Downloading PyPI packages`, `Installing PyPI packages`, `Done` — so
a determinate bar is possible. `skop_napari/_panel.py:257-263` is a working
reference, each subscription wrapped in `ensure_main_thread`.

Two traps, both established by experiment rather than from the method names:

- **`subscribe_build_error` is the stderr stream, not a failure report.** Pixi
  writes ordinary status there, `✔ The default environment has been installed.`
  included. Routing it to an error display turns every successful build into an
  error. Genuine failures raise out of `run()`.
- **Subscribing to progress is what enables it**, and it makes pixi run under
  `-vv`, so the output and error channels then carry the whole debug log.
  Filtering that to something human-facing is our job.

**Failures need the remote traceback.** The op fails in another process running
another interpreter, so a one-line status field cannot show the interesting
part. skop-napari routes it to napari's notification manager, which preserves
the traceback in history. Same here.

## Installing this, eventually

The environment that runs the first op assumes **four sibling checkouts** --
napari-ai-lab, scikit-ops, skop-napari, appose-python. Only two are named in
`pixi/pytorch_napari/pixi.toml`; the other two arrive through skop-napari's own
`[tool.uv.sources]`, which points at `../scikit-ops` and `../appose-python`
relative to its own directory. Naming them here as well makes the solve fail
with conflicting URLs, so they cannot simply be pinned locally either.

That is a development layout, not something a user with little Python can be
asked to reproduce. Before this ships:

- scikit-ops, skop-napari and appose need to be installable **by version, or
  at least by git URL** -- which means releases, or pinned revs
- skop-napari's `[tool.uv.sources]` has to stop deciding where its
  dependencies come from for everyone downstream; it is dev configuration
  leaking into consumers
- appose's `PixiInstallMonitor` needs to be in a release, or the first
  environment build is silent

And the development layout has to survive alongside it: editable checkouts are
what make an op change testable without bumping a rev in nine environments
(scikit-ops `docs/spec/fiji-front-end.md`). So the end state is two ways to
build the environment -- pinned for users, source-tree for developers -- not
one replacing the other.

## Order of work

1. **Prove skop runs StarDist headless in that pixi environment.** A script,
   numpy in, labels out, no napari, no ai-lab. This is the step that can fail
   for reasons nothing downstream can fix, and it is also where the first
   environment build is observed.
2. Adapter and registration, panel not yet wired — confirm it appears in the
   combo.
3. The `QStackedWidget` hook — confirm the generated panel renders.
4. Manual end-to-end test: select it, segment, get labels.

Each step is independently checkable. Step 1 first, always.

## Open questions

- **Does the MD slice line up?** `stardist2d_fluo` takes a `YX(C)` plane and
  ai-lab hands segmenters an MD slice. Should match for the 2-D case, unverified
  for the rest.
- **Where do the built environments actually live?** Needed for the dialog
  above. Appose decides; confirm the path rather than guessing.
- **Progress and cancellation during the run** (as opposed to the build) are
  skipped here. skop has `skop.progress()`, ai-lab has `utilities/progress_logger.py`.
  Joining them is separate work.
- **Does the generated panel look acceptable next to the hand-built one?**
  The honest reason to build this before deciding anything larger. Answered
  below: it looked fine, and was removed anyway.

## The generated panel, and why it was removed

The scope section above said two form builders would coexist, and that whether
the generated one wins "is a decision to make after seeing it work, not
before". It worked, it was seen, and the decision went the other way. Since
`SkopSegmenter` no longer generates a form, this section is the record of what
was tried, so it is not tried again by accident.

Nothing was wrong with the panel itself. What did not hold was the claim that
generating it saves writing the parameters twice, because two things a form
needs are nowhere in an op's signature.

**Which parameters the app supplies.** The image is chosen by ai-lab, and a
model by a combo. Generated straight from the signature, both appear a second
time as widgets that silently disagree with the real choice, so each needs
filtering out — a rule per segmenter, growing with each one.

**Which parameters are worth showing.** An op signature is written for every
caller, including a CLI and a notebook, so it cannot say what matters in a
panel, in what order, under what label, or which belongs behind an expert
toggle. That judgement is this repo's product and is exactly the kind of thing
[0001](0001-what-moves-to-scikit-ops.md) keeps on this side of the line.

Training made it concrete. Training parameters cannot be generated at all —
the patch directory, the model directory and the progress callback are the
app's, not the user's — so they arrived as dataclass fields like every other
segmenter's. One segmenter then carried two forms built two different ways,
and `nd_operation_widget.py` needed a rule for which to build. That rule, and
the parameter-filtering rule, are the seam between two generators rather than
features of either.

So a skop segmenter now declares its parameters as dataclass fields, like
every other segmenter, and returns them from `_op_params()`. One form builder,
one place to look. What is genuinely lost: a parameter added to an op upstream
no longer appears here on its own, and keeping the two in step is now a review
habit. A *renamed* parameter still fails loudly on the next run; a newly added
one is the quiet case to watch for.

The rest of 0004 stands. The environment split, the availability states and
the explicit registration are all still how this works.
